# Closing the LangGraph gaps: prioritized plan

Date: 2026-10-13. Base: `origin/next` at b884c736. Worktree: `~/.codex/worktrees/agent/langgraph-gaps-plan` (branch `davidkpiano/langgraph-gaps-plan`). Planning only; no library code.

## Governing constraints

- `docs/scope.md` ownership table: long-term and semantic memory is "Database or memory library"; integration point is machine `input` plus `actors`. Snapshot persistence, queues, HTTP/SSE/WebSocket are host-owned, reached through "XState snapshots, callbacks, and emitted events". A bundled "memory store" is named as the anti-pattern (scope.md:12). Non-goals list vector stores explicitly.
- `docs/roadmap.md`: "Stream adapters" and "Better interaction typing" and "Stronger request/output/event inference" are in scope. XState++ rule: forward framework capabilities, no parallel adapter layers.
- `CONTRIBUTING.md:7-16`: core only when a machine cannot express portable intent or hand it to an arbitrary host without framework glue. "Observing a run without coupling it to one vendor" and "testing control flow deterministically" are core criteria.
- Ruling 2026-09-24 (memory `langgraph-examples-port`): no published model mock, demo always needs a key, `createScriptedExecutors` / `Scripted*` were deliberately removed from `@statelyai/agent` and `@statelyai/agent/testing`. `runSeam` stayed.
- Ruling 2026-09-04 (memory `log-is-source-of-truth`): log is truth, snapshot is a verified cache.

### Prior art consulted for 2a/2e

- A2UI v0.9 (Google) and json-render (Vercel): component-tree rendering protocols; out of scope for core (UI is host-owned), a host can map the elicitation schema into either.

## Ranked gaps

### 1. Per-transition update stream (LangGraph `values` / `updates` / `messages` / `custom`)

**Current state.** All four kinds already flow through one ordered callback, `onTrace` (`src/run-agent.ts:170-243`):

- `values` = `machine.transition { snapshot, event }`, emitted by `commit` (`run-agent.ts:2618-2625`) after every root transition, including no-ops (`:2977-2983` flags `next === state` only for `result.ignored`).
- `messages` = `stream.chunk { request, chunk: string }`, emitted by core's `bindTextLogic` when the adapter calls `info.onChunk` (`run-agent.ts:1141-1187`; AI SDK `src/ai-sdk/index.ts:417`; TanStack `src/tanstack-ai/index.ts:478`). Text-only; no reasoning or tool-input deltas.
- `custom` = `emit { event }` for root-machine `enq.emit` (`run-agent.ts:2525-2532, 2572-2581`), plus the typed `on: { [type]: handler }` sugar (`:507`). Child-machine emits are not surfaced (`:2579`).
- `updates` has no equivalent: no previous snapshot, no context diff.
- Sugar: `onTransition`, `onChunk`, `onResult`, `on`, `inspect` (`:474-527`). No async-iterable anywhere in core. `examples/tanstack-ai-stream/index.ts:188-214` hand-rolls a push queue (`createChunkQueue`) to turn callbacks into an iterable; `examples/ai-sdk-ui-stream/index.ts:159-210` wires the same callbacks into `createUIMessageStream`. Neither example uses `emit` or `onTrace`.
- `AgentEventLogStore` has no append notification (`src/event-log-store.ts:20-58`); `onEvent` (`run-agent.ts:464`) is in-process only.

**Proposed design** (smallest; provider-free; keeps `onTrace` as the single emission point per `run-agent.ts:1069-1080`):

1. Enrich the existing `machine.transition` trace variant rather than add a new event bus:
   ```ts
   | { type: "machine.transition"; snapshot; event;
       changed: boolean;                       // next !== prev
       previousValue?: StateValue;             // undefined on run.start / restore
       contextPatch?: Record<string, unknown>; // shallow top-level diff, Object.is per key; removed keys as undefined
     }
   ```
   `commit(snapshot, event, prev)` takes `prev` from `transition()` (`:2960`) and `undefined` from `start` (`:2956`). `JsonSerializableTraceEvent` is derived, so JSON projection follows automatically; the pinned shape test in `src/serialize-trace-event.test.ts` needs updating. Optionally pass the same `{ changed, previousValue, contextPatch }` as a third argument to `onTransition`.
2. One async-iterable entry point, a sibling of `runAgent`, in a new `src/stream-agent.ts`:
   ```ts
   function streamAgent<TMachine>(
     machine,
     options: AgentRunOptions<TMachine> & { modes?: AgentStreamMode[] },
   ): AsyncIterable<AgentStreamPart<TMachine>> & { result: Promise<AgentRunResult<TMachine>> };
   type AgentStreamMode = "values" | "updates" | "messages" | "custom" | "trace";
   type AgentStreamPart =
     | { type: "values"; snapshot }
     | { type: "updates"; value; event; contextPatch } // skipped when !changed
     | { type: "messages"; request; chunk }
     | { type: "custom"; event }
     | { type: "trace"; event: AgentTraceEvent }; // default when modes omitted
   ```
   Internals: `runAgent(machine, { ...options, onTrace: tee })` pushing into an unbounded queue (lift `createChunkQueue` from the tanstack example) with a filter per mode. Caller-supplied `onTrace`/`onChunk`/`onTransition`/`on` are chained, not replaced. `onIdle` passes produce multiple `run.start`/`run.end` pairs with distinct `runId`s; document rather than merge.
   Decision: this belongs on `runAgent`'s level, not the runtime. `createAgentRuntime` users already own the loop and have `onTrace`; adding `events()` to `AgentRuntime` would duplicate that. `runAgent` gets no new `onUpdate` callback: `onTransition` plus the new fields is that callback.
3. Wire protocols stay in adapter subpaths (scope.md:41). After (2) lands, `examples/ai-sdk-ui-stream` and `examples/tanstack-ai-stream` are rewritten on `streamAgent` (delete `createChunkQueue`). Promoting them to `agentRunToUIMessageStream` / `agentRunToAgUiStream` exports under `./ai-sdk` and `./tanstack-ai` is a follow-up, in scope under roadmap "Stream adapters", not part of this PR.

**Touches.** `src/run-agent.ts` (trace union, `commit`, `onTransition` signature), new `src/stream-agent.ts`, `src/index.ts` export, `src/serialize-trace-event.test.ts`, new `src/stream-agent.test.ts`, `docs/observability.md` ("Live progress" section lists `streamAgent` and the new fields; trace-field list at :18), `docs/langgraph-comparison.md` construct-map row "Stream events" → `streamAgent` modes, the two stream examples.

**Effort.** M (code S for the fields, S–M for `streamAgent`, S for example rewrites).

**Risks.** `contextPatch` is shallow; nested mutations show the whole top-level key. Say so. A no-op transition still emits `values` (LangGraph does too) but must be filtered from `updates`. Unbounded queue if the consumer stalls; acceptable for an alpha, document. Child-machine states only reach `inspect`, not `values`; parity with LangGraph `subgraphs=True` is explicitly deferred.

**Exercised by.** `examples/ai-sdk-ui-stream`, `examples/tanstack-ai-stream`, `examples/parallel-streams` (interleaved `messages` keyed by `request.id`), `docs/observability.md`, `docs/langgraph-comparison.md`.

### 3. Time travel: fork from a checkpoint, edit state, resume as a branch

**Current state.** More exists than the gap statement assumes:

- Prefix replay: `replay(machine, entries.slice(0, n))` is a pure fold, documented as time travel (`src/event-log.ts:915-963`, `docs/event-log.md:98`).
- Fork: `forkEventLog(entries, upToIndex)` (`event-log.ts:734`) and `store.fork({ threadId, newThreadId, upToIndex })` (`event-log-store.ts:52`, conformance `event-log-store-conformance.ts:245-338`), documented at `docs/event-log.md:139-147`.
- Edit and resume: passing only `snapshot` restores via `machine.restoreSnapshot`, writes a fresh init-with-snapshot entry and mints a new `executionId` (`run-agent.ts:2747, 2857-2860`); `agentMeta` is checked only when `events` is also passed (`:2772`), so an edited `replay(...).persistedSnapshot` is accepted. Documented only as "Resuming from a snapshot with no log also yields a self-contained log" (`docs/persistence.md:93`).
- Nothing in `examples/` forks or replays except the Cloudflare store implementation (`examples/cloudflare-agent-host/event-log-store.ts:162`).
- **Latent bug.** A fork copies the init entry and so inherits the parent's `executionId` by design (`event-log.ts:640-659`). The idempotency key is `${executionId}:${siteId}#${n}` (`run-agent.ts:2888`). The first new model call on a forked branch therefore collides with the parent's call at the same site and occurrence, so a host that caches provider results by `callKey` (hosts.md idempotency) replays the parent's answer on the branch. The snapshot-edit path avoids this only because it mints a new id.

**Proposed design.** Mostly docs, plus one small helper that also fixes the collision.

1. `docs/event-log.md` gets a "Branch with edited state" section showing the three-line recipe (replay prefix → spread context → `runAgent(machine, { store, threadId: newId, snapshot: edited, event })`) and the rule "snapshot only at a quiescent index" (persistence.md:91).
2. Helper in `@statelyai/agent/log` (`src/event-log.ts`, re-exported from `src/log/index.ts`):
   ```ts
   forkThread(store, machine, { threadId, newThreadId, upToIndex, update?: (persisted) => persisted }): Promise<AgentLogEntry[]>
   ```
   Without `update`: `store.fork`, then rewrite the new thread's init entry with a fresh `executionId` and `metadata.forkedFrom: { threadId, executionId, upToIndex }` (mirrors `migratedFrom` on the version bridge, `run-agent.ts:2847-2855`). With `update`: replay the prefix, apply the edit, seed the new thread with a single `initEntry(machine, { snapshot }, { metadata })`.
   Decision to make explicit in the PR: whether `forkEventLog` / `store.fork` themselves should stop inheriting `executionId`. Recommendation: yes, mint a fresh one and carry lineage in `forkedFrom`, because the inherited id is what makes `callKey` collide. This changes a documented statement (`docs/event-log.md:141`) and the conformance suite.
3. New example `examples/time-travel` (or `branch-and-edit`): run to idle, fork at an earlier index, edit a context field, resume the branch, show both threads' logs diverge; test asserts the callKeys differ.

**Touches.** `src/event-log.ts`, `src/event-log-store.ts` (+ in-memory impl), `src/event-log-store-conformance.ts`, `src/log/index.ts`, `docs/event-log.md`, `docs/persistence.md`, `docs/langgraph-comparison.md` (row for "time travel / `update_state`"), new example + test.

**Effort.** S for docs; M with the helper and the executionId change.

**Risks.** Changing fork lineage semantics touches the Cloudflare host store in `examples/`. Editing a snapshot bypasses the machine's typed transitions; the docs must say the edited snapshot is unverifiable against the parent log and starts a new lineage. Keep the `update` callback on the persisted snapshot, not a context-only patch, so parallel state values and children can be edited consistently (or rejected).

**Exercised by.** new `examples/time-travel`, `examples/cloudflare-agent-host` (store fork), `docs/event-log.md`, `docs/persistence.md`.

### 6. Store / long-term memory abstraction (gap 3)

**Current state.** `examples/long-term-memory/index.ts` models the store as `string[]` in machine `input` `{ userId, memories }` (`:233-236`) and `output.memories` (`:402-420`); the host persists output and feeds the next run (`:534-536`). Recall is an `actors` entry (`searchMemories`, `:124-150, :246-249`), save is a pure `choice` state with dedupe and a `MAX_MEMORIES` cap (`:383-397`). Header says outright there is no `BaseStore` handle (`:50-53`). The only store-like interface in `src/` is `AgentEventLogStore` (`src/event-log-store.ts:20-58`): append-only, thread-keyed, optimistic concurrency, no key/value, namespace, search, update or delete.

**Decision: neither a core interface nor a new abstraction.** `docs/scope.md:36` assigns long-term memory to a database or memory library with `input` + `actors` as the integration point; `scope.md:12` names a bundled memory store as the anti-pattern; CONTRIBUTING.md:16 lists vector stores as out. A `BaseStore` with namespaces and search is a storage product, not control flow, and would conflict with the append-only, log-is-truth design of the one store core does own. Shipping it would also set the precedent scope.md exists to prevent.

**What ships instead** (docs only):

1. `docs/patterns.md`: a "Long-term memory" pattern section: the store is host-owned; a recall actor and a capped save state are the machine's two touchpoints; memory handles (ids, not blobs) live in context; the host chooses KV, vector, or SQL.
2. `docs/langgraph-comparison.md`: a construct-map row "`BaseStore` / `store.put` / `store.search`" → "host store behind an `actors` entry; see patterns.md and `examples/long-term-memory`", and a sentence in the prose list after the map saying this is deliberate.
3. Fix the stale wording at `docs/scope.md:40`, which still lists snapshot persistence as `result.persist()` only, to mention the event log store.

**Touches.** `docs/patterns.md`, `docs/langgraph-comparison.md`, `docs/scope.md`.

**Effort.** S. **Risks.** Users coming from LangGraph may still ask for it; the comparison row is the answer.

**Exercised by.** `examples/long-term-memory`, `docs/patterns.md`.

### 7. Durable log store: recipes, not a package (added 2026-10-14)

**Why it's here.** After A–C, the first obstacle a LangGraph user hits is "where do I put the log?" LangGraph ships `MemorySaver`, `SqliteSaver`, `PostgresSaver`. We ship the interface, an in-memory implementation, and a conformance suite.

**Current state.** `AgentEventLogStore` is four methods: `append`, `read`, `length`, `fork` (`src/event-log-store.ts:20-58`). `createInMemoryEventLogStore` is the reference (`:92-169`). `assertEventLogStoreConformance(createStore, { describe, it })` is exported from `@statelyai/agent/log` (`src/log/index.ts:44-45`) and documented in two sentences (`docs/event-log.md:177-183`). `examples/cloudflare-agent-host/event-log-store.ts` is the only host-written store, and it runs the suite (`:24`). No SQLite or Postgres recipe exists anywhere.

**Decision.** No bundled store. It would not break "the machine runs anywhere" (the machine never names a store), but it contradicts `docs/roadmap.md` ("storage, queues, retries, and interruption policy: host frameworks") and `docs/scope.md:40`, and it starts an open-ended adapter queue. Same policy as the model mock: show it, don't ship it.

**Proposed design** (docs and examples only):

1. `docs/event-log.md` "Stores" section is rewritten to lead with the contract and the suite: "implement four methods, run `assertEventLogStoreConformance`, you're done". Include the SQL shape (`(thread_id, index)` primary key, append in one transaction with a length check).
2. `examples/stores/` (or three sibling example dirs, per the one-flat-directory rule): `sqlite` (`better-sqlite3`, ~60 lines), `postgres` (`pg`, ~60 lines), and a pointer to `cloudflare-agent-host`'s Durable Object store. Each has a test that runs the conformance suite; SQLite in-memory runs in CI, Postgres is gated on a `DATABASE_URL` env var and skipped otherwise.
3. `docs/langgraph-comparison.md`: a construct-map row "`MemorySaver` / `SqliteSaver` / `PostgresSaver` → `createInMemoryEventLogStore`, or your store checked by `assertEventLogStoreConformance`; see the store recipes".
4. `docs/persistence.md` "Framework storage" links the recipes.

**Touches.** `docs/event-log.md`, `docs/persistence.md`, `docs/langgraph-comparison.md`, new example dirs with tests, `examples.test.ts` registration if required. No `src/` change.

**Effort.** S–M (the recipes are small; the Postgres CI gating is the fiddly part).

**Risks.** Recipes drift from the conformance suite as it grows; running the suite in CI is the mitigation. A user may still ask for a package; the comparison row answers it.

**Exercised by.** the new store examples, `examples/cloudflare-agent-host`, `docs/event-log.md`.
